# Habit Tracker

REST API для управления полезными привычками и отслеживания их выполнения.

Проект разработан на Django REST Framework и предоставляет API для создания, редактирования и отслеживания привычек пользователя. В проекте также реализованы фоновые задачи с использованием Celery и Redis, планирование периодических задач через Celery Beat, работа с PostgreSQL, контейнеризация приложения и reverse proxy через Nginx.

## О проекте

**Habit Tracker** — серверное приложение для формирования и отслеживания привычек.

Пользователь может создавать собственные привычки, указывать параметры их выполнения и контролировать регулярность выполнения.

Backend реализован в формате REST API, благодаря чему с приложением могут взаимодействовать веб-клиенты, мобильные приложения и другие потребители API.

Проект построен с использованием разделения ответственности между основными компонентами:

* Django отвечает за основную бизнес-логику;
* Django REST Framework предоставляет REST API;
* PostgreSQL используется для хранения данных;
* Redis используется как брокер сообщений;
* Celery выполняет фоновые задачи;
* Celery Beat запускает периодические задачи;
* Gunicorn используется как WSGI-сервер;
* Nginx работает как reverse proxy;
* Docker обеспечивает контейнеризацию компонентов приложения;
* GitHub Actions используется для автоматизации CI/CD.

## Основные возможности

### Работа с пользователями

API предоставляет возможности для:

* регистрации пользователей;
* аутентификации;
* получения информации о текущем пользователе;
* работы с пользовательскими данными;
* разграничения доступа к данным пользователей.

### Работа с привычками

Пользователь может:

* создавать привычки;
* просматривать список своих привычек;
* получать информацию о конкретной привычке;
* редактировать привычки;
* удалять привычки;
* отслеживать параметры выполнения привычки.

### Работа с API

API построено на основе принципов REST и использует стандартные HTTP-методы:

| Метод    | Назначение           |
| -------- | -------------------- |
| `GET`    | получение данных     |
| `POST`   | создание объекта     |
| `PUT`    | полное обновление    |
| `PATCH`  | частичное обновление |
| `DELETE` | удаление объекта     |

## Архитектура проекта

Приложение состоит из нескольких взаимодействующих компонентов:

```text
                         ┌─────────────────┐
                         │     Client      │
                         │  Web / Mobile   │

                                  │

                         │      Nginx      │

             │ PostgreSQL  │             │    Redis    │
```

## Фоновые задачи

Для выполнения фоновых операций используется **Celery**.

Использование фоновых задач позволяет не выполнять длительные или периодические операции непосредственно во время HTTP-запроса.

Общая схема:

```text
Django
  │
  │ task
  ▼
Redis
  │
  │ message
  ▼
Celery Worker
  │
  ▼
Background Task
```

Это позволяет разгрузить основной web-процесс и выполнять задачи независимо от пользовательского запроса.

---

## Celery Beat

Для запуска периодических задач используется **Celery Beat**.

Celery Beat отвечает за расписание выполнения задач и передает задачи Celery Worker через Redis.

Архитектура:

```text
Celery Beat
     │
     │ scheduled task
     ▼
   Redis
     │
     ▼
Celery Worker
     │
     ▼
Task execution
```

Для хранения расписания и управления периодическими задачами используется `django-celery-beat`.

## PostgreSQL

В качестве основной базы данных используется **PostgreSQL 16**.

PostgreSQL отвечает за постоянное хранение:

* пользователей;
* привычек;
* связанных объектов;
* данных Django;
* данных периодических задач.

В Docker Compose PostgreSQL работает как отдельный сервис.

Использование отдельного контейнера позволяет изолировать базу данных от web-приложения и остальных компонентов системы.

## Redis

**Redis 7** используется в качестве брокера сообщений для Celery.

Redis обеспечивает передачу задач между Django/Celery Beat и Celery Worker.

В архитектуре проекта Redis является связующим компонентом между планировщиком задач и обработчиками фоновых операций.

## CI/CD

Для автоматизации процессов разработки используется **GitHub Actions**.

CI/CD pipeline предназначен для автоматической проверки изменений перед их объединением с основной веткой разработки.

Текущий workflow включает следующие этапы:

```text
Push / Pull Request
        │
        ▼
Checkout
        │
        ▼
Setup Python
        │
        ▼
Install dependencies
        │
        ▼
Database migrations
        │
        ▼
Run tests
        │
        ▼
Build Docker images
```

CI запускается:

* при push в feature-ветки;
* при создании Pull Request в `develop`.

Это позволяет автоматически проверять изменения до их объединения с веткой разработки.

В дальнейшем pipeline используется также для автоматизации deployment на удаленный сервер.

## Безопасность

Конфиденциальные настройки приложения не должны храниться непосредственно в исходном коде.

Для конфигурации используются переменные окружения.

К конфиденциальным данным относятся:

* `SECRET_KEY`;
* пароль PostgreSQL;
* учетные данные базы данных;
* параметры production-окружения;
* SSH credentials для deployment.

Файл `.env` не должен добавляться в Git-репозиторий.

Для этого `.env` должен находиться в `.gitignore`.

## Git Workflow

В проекте используется ветвление с отдельной feature-веткой и веткой `develop`.

Основной рабочий процесс:

```text
feature/habit-trecker
          │
          │ Pull Request
          ▼
       develop
          │
          │ CI/CD
          ▼
     Deployment
```

Разработка новых возможностей выполняется в feature-ветках.

После завершения работы создается Pull Request в `develop`.

GitHub Actions автоматически проверяет Pull Request.

Изменения могут быть объединены с `develop` после успешного прохождения CI.
